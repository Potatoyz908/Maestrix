## 2. Regras de trabalho (inegociáveis)

1. **Donos de arquivo.** Você só edita os arquivos da sua seção (§4). Em arquivo de outro dono (ex.: `window.py`, `InterAgentServer.swift`, `CLIRouter.swift`): hunk mínimo, releia o arquivo imediatamente antes, nunca reformate. Precisa de algo de outro dono? Use o **contrato de API do §3** e, se faltar, peça ao Maestro (`maestri ask "Maestro #2" ...`).
2. **Git.** Branch `feat/linux-port`; índice **compartilhado**: commite só os seus caminhos/hunks (`git commit --only <paths>` ou índice temporário), nunca `git add -A`, `git commit -a` nem `git reset -- .`; nunca na `main`; **sem push**. Conventional Commits com emoji. Termine a mensagem com: `Co-Authored-By: Claude <noreply@anthropic.com>`.
3. **Testes.** Não rode a suíte completa nem e2e durante a implementação (uma rodada por sprint: Monitor, §5). Permitido: `py_compile`, import, `swift build -Xswiftc -use-ld=lld` e, no máximo, os testes que você acabou de escrever, por filtro, **sempre isolados** (§2.5). GUI só em Xvfb `DISPLAY=:99`, nunca no display do usuário.
4. **Linux/Swift:** `swift build -Xswiftc -use-ld=lld` (não rode `swift test` inteiro).
5. **Isolamento de dados (crítico).** Nenhum teste, script ou experimento toca `~/.open-maestri`, `~/.claude` ou `~/.codex` reais. Use `OPEN_MAESTRI_DATA_DIR=<tmp>`; para skills, o instalador usa `<dataDir>/skills` quando essa variável está definida (§3 K5). A guarda do `conftest` falha o run se o diretório real mudar. Use `tests/data_dir_isolation.py::start_isolated_server()` para subir o servidor de teste. **Não mate nem reinicie processos do usuário**; não use `pkill` fora dos processos que você mesmo subiu.
6. **GTK4/Python 3.14.** Antes de `super().close()` em diálogo modal: `set_visible(False); set_modal(False); set_transient_for(None)` em try/except. Timers e tick callbacks removidos em `_cleanup()`.
7. **Formato Maestri imutável:** `workspace.json` schemaVersion 2, `NodeContent` como `{"tipo": {"_0": ...}}`, frames `[[x,y],[w,h]]`. Campo novo só como opcional, e testado no round-trip.
8. **Ícones, não emojis** (SVG outline `maestri-*-symbolic`; módulo `gtk4-ui/src/ui/iconography.py`).
9. **Relatório final** (`maestri ask "Maestro #2" "..."`): o que mudou, arquivos, hashes de commit, **o que NÃO verificou**, e o que dependeu de contrato de outro agente. Dê um status por item da sua seção: FEITO / PARCIAL / NÃO FEITO + motivo.

## 3. Contratos entre agentes

**K1 — Ids de nó e terminal.** No macOS `CanvasNode.id == TerminalContent.terminalId`. No port a GUI gerava dois uuids (`window.py` ~1577/1602/1701 e `context_menus.py` ~260).
 - GUI (Vertice, Pixel nos seus pontos): todo terminal novo nasce com `TerminalContent(id=node_id, terminal_id=node_id)`, ids em MAIÚSCULAS.
 - Servidor (Codice): para workspaces antigos onde os ids diferem, `POST /api/connections` e `restoreConnections` resolvem cada ponta para o **id do terminal** lendo `workspace.json` (nó → `content.terminal._0.terminalId`); lookups por `X-Terminal-ID` funcionam com qualquer um dos dois.

**K2 — Nós e conexões criados pelo servidor (CLI) aparecem no canvas.** Quando um handler (`note create`, `recruit`, `dismiss`, `connect`, `portal create`, `role assign`…) cria/remove nó ou conexão, o servidor: (1) persiste em `workspace.json` de forma atômica, respeitando a proteção contra snapshot velho já existente; (2) publica em `/ws/events` via `EventBroadcaster.publish(type:workspaceId:payload:)`:
 - `nodeAdded {workspaceId, node:<CanvasNode JSON idêntico ao do workspace.json>, terminalCount}`
 - `nodeRemoved {workspaceId, nodeId, terminalCount}`
 - `connectionCreated {workspaceId, connection:<JSON da conexão>, kind}`; `connectionRemoved {workspaceId, connectionId}`
 A GUI (Vertice, em `window.py`/`api.py`, que já emitem `node-added`/`node-removed`/`connection-created`/`connection-removed` no bus): se `workspaceId` for o documento aberto e o id for desconhecido, adiciona ao `payload` e ao canvas **sem re-postar** (marca origem `server`, sem eco). Se for outro workspace, só atualiza o badge. Remoção idem.

**K3 — Ponte de portal (servidor → GUI).** `LinuxPortalManager: PortalManaging` (Nexus, no alvo do servidor, injetado em `Sources/Server/main.swift` via `PlatformHooks.portalsService`). Cada operação publica `portalCommand {requestId, workspaceId, portalId, op, args}` em `/ws/events` e aguarda `POST /api/portal-results {requestId, ok, result|error}` (timeout 30 s). `op` ∈ `create|close|navigate|back|forward|reload|info|snapshot|text|html|screenshot|evaluate|click|fill|type|key|hover|scroll|drag|wait|select|check|focus|logs-start|logs`. `screenshot` devolve PNG em **base64**. Sem GUI conectada ou sem resposta: retorna string de erro legível (`error: portal view unavailable ...`), **nunca** `fatalError`. Executor na GUI: Arquiteto (`canvas-cairo/maestri_canvas/portal_bridge.py`, classe `PortalBridge(canvas_widget, client)` com `handle_event(evt: dict)`), ligado por **uma linha** de Vertice em `window.py`. Resolução de portal por **nome** respeitando as conexões do chamador.

**K4 — `ask` com agentes reais.** Servidor (Codice): o terminal recebe `agentType` do preset/comando no `POST /api/terminals` (`claude`→`claude_code`, `codex`→`codex`, `gemini`→`gemini_cli`, `opencode`→`open_code`, senão `generic_shell`; a GUI envia o campo, Vertice). O `TerminalActivityMonitor` publica `terminalBecameIdle` para terminais de agente (silêncio ≥ 3 s após saída). `ask`: escreve o texto, aguarda 150 ms e envia **Enter separado**; para agente espera `terminalBecameIdle` (teto 20 min), para shell usa o prompt (teto 30 s); devolve o último trecho da saída. Implemente também `ask --batch '<json>'` (paralelo, resultado JSON `[{name,output|error}]`) e `ask --raw "<texto com \n \t \e \xNN>"`.

**K5 — Skills.** `SkillInjector.installSkillsIfNeeded()` é chamado em `Sources/Server/main.swift` na subida e em mudança de preferências. Diretórios-alvo: `prefs.skillPaths` ativos; se vazio, padrão Linux = `~/.claude/skills` **exceto** quando `OPEN_MAESTRI_DATA_DIR` está definido (aí `<dataDir>/skills`, isolado para testes). Idempotente. Conteúdo: as skills `open-maestri`, `open-maestri-portal`, `open-maestri-manager`, mais `open-maestri-routines` e `open-maestri-workspace` quando os comandos existirem. **Não** criar um alias `maestri` (conflita com o app Maestri oficial desta máquina); o CLI é `omaestri`. O PTY recebe `MAESTRI_CLI=<caminho do omaestri>` e o diretório dele no `PATH` (Nexus, `POSIXPtyProcess.swift`).

**K6 — Restaurar conexões.** Na subida do servidor (todos os workspaces do manifest) e a cada `POST /api/workspace` (salvar), o servidor reconstrói o `ConnectionManager` a partir das conexões do `workspace.json` (terminal↔terminal, terminal↔nota, nota↔nota, terminal↔portal, portal↔portal), reaproveitando os ids persistidos e limpando as do workspace antes de recriar. `DELETE /api/connections/:id` e remoção de nó revogam a permissão (`disconnect` pelo id persistido) e emitem os eventos de K2.

**K7 — CLI de notas.** Escopo = notas conectadas ao terminal chamador (inclui cadeia nota↔nota); nome exato primeiro, `contains` só como fallback dentro do escopo; notas de path custom resolvidas pelo `customPath` do nó; `list` mostra o nome real da nota (lido do nó, sem `NoteRegistry`); `note read "N" [offset] [limit]` no formato de `docs/reference/maestri-cli.md` (`[14 lines total]` / `[lines 10-14 of 14]`, linhas numeradas); `note create ["texto"] [--name N] [--color C]` cria o nó **e** a conexão com o terminal via K2; `note delete "N"` remove o nó (K2).

**K8 — Modo Maestro.** `isManager` (já serializado em `models/node.py`) é gravado pela GUI quando o diálogo marca "Maestro" ou quando o menu "Enable Maestro" é usado (Pixel entrega o valor; Vertice persiste). `recruit` (Codice): exige `isManager` do nó chamador lido do `workspace.json` (agora ids iguais, K1), cria PTY + **nó + conexão** via K2 posicionado abaixo do Maestro (grade: x = frame.x + i·(w+24), y = frame.y + h + 48), aceita `--dir`, `--icon`, `--color`, `--role`, `--preset`, `--replace`, `--floor`; `dismiss` remove nó + conexão; `connect` liga recruta a terminais **e notas**; `role assign` reinicia o agente mantendo posição/nome/conexões.

**K9 — APIs de canvas (Arquiteto fornece; Pixel/Vertice consomem).**
 - `CanvasController.begin_connect_mode()` / `cancel()`; tecla `L` entra no modo (linha segue o cursor; clicar no 2º nó emite o sinal já existente `connection-requested(a, b)`).
 - `Scene.hit_connection(point) -> ConnItem | None`; clique direito sobre corda produz alvo `ConnectionTarget` com `.conn_id`. O menu (Pixel) chama `win.delete_connection(conn_id)` (Vertice implementa: `client.delete_connection` + canvas + payload + K2).
 - `NodeFrame.set_number_badge(n: int | None)`; `CanvasWidget.show_number_badges(on: bool)` enquanto Ctrl está pressionado; `CanvasWidget.jump_to_terminal(n: int)` foca o N-ésimo terminal (1-9, ordem de criação); atalhos Ctrl+1..9 em `interaction.py`.
 - `interaction.py` chama `win.copy_selected_nodes()` (Ctrl+C) e `win.paste_nodes(at=None)` (Ctrl+V) — ver K10.
 - Sinais do widget de canvas: `node-lock-changed(node_id, locked)` e `node-z-changed(node_id, z)` (Vertice persiste em `CanvasNode.is_locked` / `z_index` e os aplica ao carregar).

**K10 — Área de transferência de elementos.** Vertice implementa em `window.py`: `copy_selected_nodes()`, `copy_node(node_id)`, `paste_nodes(at=None)`. Mime `application/x-maestri-element` com JSON `{"nodes":[<CanvasNode dict>...], "connections":[...]}`; o paste gera ids novos (K1), nome com " Copy" só se colidir; texto com URL cria Portal; texto livre cria Nota; sem conteúdo reconhecido, não faz nada. Pixel (menu de contexto) e Arquiteto (teclas) apenas chamam.

**K11 — Partituras.** Contrato REST em `docs/linux-gtk-sprint7-spec.md` §2 (Nexus implementa no servidor; armazenamento em `<dataDir>/partituras/<id>.json`; `GET/POST /api/partituras`, `DELETE /api/partituras/:id`, `POST /api/partituras/:id/apply?workspace=` que cria nós/conexões via K2). CLI `omaestri partitura list|save|apply|delete`. UI (Pixel): submenu **Partituras ▸** (lista + "Save layout…") no menu do canvas e do nó; usa `client` via Vertice: `win.save_partitura(name, node_ids|None)` e `win.apply_partitura(id, at)`.

**K12 — Floors: hooks e variáveis.** Nexus: `POST /api/floors/:id/hooks/run {phase: "setup"|"run"|"teardown", hookId?}`; Setup roda no `POST /api/floors`, Teardown no `DELETE`; `POST /api/terminals` aceita `floorId` e injeta `MAESTRI_FLOOR_NAME`, `MAESTRI_BRANCH_NAME`, `MAESTRI_FLOOR_PATH`, `MAESTRI_ROOT_PATH`, `MAESTRI_PROJECT_NAME` no PTY. A GUI (Vertice) envia `floorId`; a UI de hooks (Sentinela) usa `PATCH /api/floors/:id` (já guarda `hooks`) e o endpoint de run.

**K13 — Terminal: reload/unload/scrollback.** Nexus: `POST /api/terminals/:id/restart` (mata e recria o PTY com os mesmos parâmetros), `POST /api/terminals/:id/unload`; scrollback persistido em `<dataDir>/workspaces/<wsId>/terminals/<terminalId>.scrollback` (gravar periodicamente e no encerramento; restaurar no replay ao recriar a sessão); evento `terminalExited {workspaceId, terminalId, exitCode}`. A GUI chama via `win.reload_terminal(node_id)` / `win.unload_terminal(node_id)` (Vertice); o menu (Pixel) só chama esses métodos.
